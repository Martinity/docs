The game's cutscenes are **859 EVD scripts packed into disk file 186**, in 107
event files numbered 400 to 811. A second, much smaller container, disk file
187, holds 34 scripts that run inside scripted battles. This page is about the
container: how the engine addresses a script inside it, what is there, and the
loading path. The [EVD format](../../evd/format/) pages describe the bytecode
each script is written in; [How an event starts](../starting/) describes what
runs it.

Everything on this page was read from the USA disc image and from the debug
build's `step0_00` overlay, with the linker map's names. The member layout was
verified by walking the container for every one of the 859 scripts.

## 1. Addressing: there are no filenames

Nothing in the game refers to a file by name; the only identifier is a **TOC
index**, and the data centre's own index — disk file 5 — says what each one
holds. `CRadiDataCenter::LoadDataIndex` (`0x002C28D0`) reads file 5 whole and
runs `Rel2AbsKodsAddr` on it, after which its Kods slots are pointers to
tables. Two of those tables are the event tables <Tag kind="confirmed" />:

| Slot of disk file 5 | Table | Entries | Addressed disk file |
|---:|---|---:|---|
| `0` | The event files. Pointer kept at data centre `+0x08`. | 812 (one is the terminator) | **186** |
| `9` | The high-bit event files. Pointer kept at `+0x2C`. | 8 (one is the terminator) | **187** |

`CRadiDataCenter::GetEventScriptFileDatas(id, &file, &sector, &size)`
(`0x002C27F0`) is the whole lookup:

```asm
002C2810  lw    v1, 8(a0)             ; data centre index; -1 if not loaded
002C2828  andi  v0, a1, 0x8000        ; bit 15 of the event file id
002C282C  bnez  v0, high
002C2834  lw    a0, 8(v1)             ; table: slot 0 of file 5
002C283C  addiu s0, zero, 0xba        ; disk file 186
002C2840  lw    a0, 0x2c(v1)          ; high: table: slot 9 of file 5
002C2848  addiu s0, zero, 0xbb        ; disk file 187
002C2850  and   a1, a1, 0x7fff        ; strip the bit
002C285C  jal   GetKodsDataOffset     ; (table, id, &offset, &size)
002C2878  lw    v0, 0x58(sp)          ; size 0 = no such event file
002C2890  sw    s0, (s3)              ; disk file
002C289C  srl   v1, v1, 0xb           ; byte offset -> 2048-byte sector
```

So an **event file id** is an index into an external Kods table — the same
header shape the character archives use, where the table describes byte
ranges of another file: entry `i` gives the byte range of event file `i`
inside disk file 186, and its size is the distance to the next entry, so the
last slot is a terminator and ids run `0`–`810`. Only 107 of them are live. **Bit 15 of the id selects the
second table and disk file 187**; `Command_06`'s argument bit 0 sets it
(`0x002EB47C`), which the decompiler spells `force_high_bit=1`. No shipped
script does so ([§3](#3-disk-file-187)).

## 2. The member layout

Each event file is itself an internal Kods whose members are the scripts,
numbered from 1; each member is SLZ-compressed and, decompressed, is another
Kods holding the bytecode and the script's messages. `GetScriptAddress` mode 1
(`0x002E3A98`–`0x002E3C78`) reads it exactly so, and the walk over the disc
confirms it for all 859 scripts <Tag kind="confirmed" />:

```text
disk file 186                       2,940,928 bytes on the USA disc
 └─ event file <id>                 byte range from the event table (slot 0 of file 5)
     └─ Kods, member <script>       internal Kods; the control word's entry count is the
         │                          highest script number + 1, and member 0 is never used
         └─ SLZ                     one compressed block
             └─ Kods { 0: EVD\x01 bytecode, 1: RMF1 messages }
```

Three files, read from the disc:

| Event file | Outer Kods | Control word | Members | Member 1 |
|---:|---:|---|---|---|
| `400` | 6,144 bytes | `0x00020002` | 1 script | SLZ 6,128 B → Kods 13,160 B → `EVD` 11,212 B + `RMF1` 1,932 B |
| `500` | 75,776 bytes | `0x00020013` | 18 scripts | SLZ 7,112 B → Kods 20,276 B → `EVD` 18,048 B + `RMF1` 2,212 B |
| `810` | 12,288 bytes | `0x00020015` | 20 scripts | SLZ 704 B → Kods 1,436 B → `EVD` 1,180 B + `RMF1` 240 B |

The control word's low 16 bits are the entry count and bits 16–19 the offset
shift (`2`, so stored offsets are in words); the `+1` in the count is slot 0,
which holds nothing in any event file. That is why script numbers start at 1
and why `SetScriptNumber`'s script number is used as the member index without
adjustment.

The `RMF1` member is the script's own dialogue, in the
[RMF message format](../../rmf/container/); `talk_rmf(message_id=N)` in a
script indexes it. It is the reason a script and its text always ship together
and never drift apart.

`GetScriptAddress` caches each decompressed script under `this+0x2A44` by
script number, so a script is decompressed once per file load.

## 3. Disk file 187

The high-bit table addresses a 45,056-byte container holding **7 event files
with 34 scripts**, ids `1`–`7` — `0x8001`–`0x8007` as a script would pass
them. They are the scripted battles: each file is one chain from its script 1,
none loads a map, and they drive the battle character commands and in-fight
dialogue. **No script in any corpus loads a high-bit file**, so what starts
them is the battle code, not the field; which call site is not established
([Chains §7](../chains/#7-disk-file-187-the-in-battle-scripts)).

## 4. The other script containers

Event files are one of five places the engine keeps EVD scripts, and the
[start modes](../../evd/format/#42-script-sources-and-the-two-id-spaces) name
them. For the event chain the other four matter because they *launch* events:

| Container | Where | Scripts | Read by |
|---|---|---:|---|
| **Map script tables** | each map archive's nested Kods (slot 2); member 0 is the map's init script | 8,709 in 882 maps | mode `3` |
| **Character action data** | datacenter kind 7 of the character's own archive, one entry per schedule list number; sub-slots `0` mode-4 act script, `1` `RMF1`, `2` mode-2 act script, `4` talk script, `5` kick script | 11,322 payloads in 523 entities | modes `2`, `4`, `0xC`, `0xD` |
| **Schedule lists** | disk file 185, one 2,048-byte block per person through file 5's slot 7 | 734 | the person's own slot, mode `0xF` |
| **Selection scripts** | disk file 184, one Kods of 278 scripts | 278 | mode `0xB` |

The animation archives (kinds 0–5) hold another 10,815 EVDs — frame-triggered
expression and effect scripts — and none of them launches an event
([Chains §5g](../chains/#5g-every-character-file-walked)).

## 6. Loading a file

`CRadiScript::LoadScriptFile(int id)` (`0x002E4660`) does not read anything
itself <Tag kind="confirmed" />. It stops any slot that is a **pending** mode-1
start — status byte 0 bit 6 set — since the file it was waiting for is being
replaced (`0x002E4688`–`0x002E46BC`); then picks record `(id >> 15) & 1` — the
low or high table — and stores the id into that record's `+0x1C`
(`0x002E46F0`–`0x002E4740`). The ids `−1` and `−2` select records 0 and 1 the
same way and are later served from a built-in table at `0x0037E948` rather
than from the disc. The two records are `0x20`-byte file objects at `this+0x2A00`,
one per event table, with the current index in the low nibble of `+0x2A40`.

`FuncRun`'s tail then services the request each frame: it resolves the id
through `GetEventScriptFileDatas` and starts an asynchronous
`CFileObject::LoadFile`. A mode-1 `SetScriptNumber` issued before the load
completes is parked in its slot with bit 6 and re-issued by `FuncRun` on the
frame `CFileObject::GetLoadStatus` reports bit `0x40`
([How an event starts §3](../starting/#3-event-to-event)).

**"The current event file" is game state.** The engine sets no event file per
map. `LoadScriptFile` has eleven callers in the whole image and its overlays,
and on the field they are three: `Command_06` in a script, `CGame::Step1`'s
post-battle path reading the queued battle event, and `CGame::Step4`'s
schedule step. Whatever was loaded last is what a bare `start_script(mode=1,
…)` reaches, which is the convention 800 of the 881 map init scripts rely on
([How an event starts §4.1](../starting/#41-the-init-script-and-its-two-conventions)).

## 7. What is not established

- Which battle-code call site loads a high-bit file and starts the file-187
  scripts.
- What event file 52 is: an unlabelled entity's talk script loads it and
  starts its script 10, and it is not one of the 107 files in the table above
  ([Chains §5g](../chains/#5g-every-character-file-walked)).
- The role of `+0x2A41`, the byte beside the record index, which two engine
  functions set and clear single bits in.
